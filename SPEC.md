# SPEC – Familien-Einkaufshelfer (MCP)

Status: **draft for review** · Scope of this document: v1 (phases 1–3)

## 1. Purpose

An MCP server that turns structured shopping requests from an AI client (Claude) into a clean shopping list. It resolves requested terms to saved favourites, reports ambiguities instead of guessing, and merges repeated additions of the same product. Language understanding and the dm product search happen in the AI client; this server is deterministic and never calls dm.

## 2. Phases

| Phase | Content |
|---|---|
| **1 – Core (first slice)** | Core logic (matching, product identity, merging, idempotency), JSON storage, MCP tools `resolve_items`, `add_to_shopping_list`, `get_shopping_list`, Vitest unit and storage integration tests. Tooling: TypeScript strict, Zod, Prettier, Vitest. |
| 2 – Favourites & dm | MCP tools `get_favorites`, `save_favorite`; `.mcp.json` with this server and dm's public MCP server; documented manual run. |
| 3 – UI | Small Next.js UI (German): favourites (read-only), shopping list, mark as bought, remove; Playwright E2E. ESLint and GitHub Actions CI are added in this or a later phase. |

Only phase 1 is specified in full detail. Phases 2–3 are specified as far as they constrain the phase 1 data model.

## 3. Data model

All persisted data lives in one JSON document (`StoreFile`). Timestamps are ISO 8601 UTC strings. IDs are UUID v4, generated by the server. Text fields are stored trimmed (§4.1).

```ts
type StoreFile = {
  version: 1;
  favorites: Favorite[];
  list: ListEntry[];
  processedRequests: ProcessedRequest[];
};

type ProductRef = {
  name: string;                 // display name, 1–200 chars; NOT used for identity
  category?: string;            // free text, 1–100 chars
  dmArticleNumber?: string;     // dm article number, digits only, 1–13 chars
  dmUrl?: string;               // dm product URL, stored normalised (§4.2)
};

type Favorite = ProductRef & {
  id: string;
  category: string;             // required for favourites
  aliases: string[];            // 0–20 entries, each 1–100 chars, unique store-wide after normalisation
  createdAt: string;
};

type ListEntry = {
  id: string;
  product: ProductRef;          // snapshot; identifiers may be completed on merge (§4.4)
  favoriteId?: string;          // set if the entry was created via a favourite
  quantity: number;             // integer 1–99
  status: "open" | "bought";
  addedAt: string;
  boughtAt?: string;            // set when status becomes "bought" (phase 3)
};

type ProcessedRequest = {
  requestId: string;
  payloadHash: string;          // SHA-256 of the canonical JSON of the request items
  result: AddResult;            // the original successful result (§6.2)
  processedAt: string;
};
```

## 4. Rules

### 4.1 Text fields and normalisation

- Every text input (names, categories, aliases, search terms) is trimmed first. Length limits apply to the trimmed value, and it must contain at least one character. Whitespace-only values are invalid (`VALIDATION_ERROR`).
- `normalize(s)` = Unicode NFC → trim → collapse internal whitespace to a single space → `toLocaleLowerCase("de-DE")`. No other folding (no ä/ae, ß/ss, plural or fuzzy handling).
- Aliases must be non-empty after normalisation.

### 4.2 Product identity

Identifiers of a product:

- **DAN** – `dmArticleNumber`.
- **URL** – normalised `dmUrl`: scheme `https`, host lower-cased, `dm.de` mapped to `www.dm.de`, query string and fragment removed, trailing slash removed; path kept as is. Only hosts `www.dm.de` and `dm.de` are accepted. The path must not be empty after normalisation: the dm start page (e.g. `https://www.dm.de/`, also with query or fragment) is not a product URL and is rejected with `VALIDATION_ERROR`, even if a DAN is given.
- **Favourite** – `favoriteId`, only for list entries created via a favourite.

When an item references a favourite, it carries that favourite's DAN and URL. Two products A and B are **the same product** if:

1. both have a DAN → the DANs are equal;
2. otherwise, both have a URL → the URLs are equal;
3. otherwise, neither has a DAN or URL → both come from the same `favoriteId`;
4. in all other cases they are different products.

A product is **never** identified by its name.

**Conflicts** fail the whole request with `PRODUCT_IDENTITY_CONFLICT`:

- Both products have a DAN, the DANs differ, but the URLs are equal.
- An item is the same product as more than one open entry. Example: one entry has only DAN 123 and another has only URL X, and the item has DAN 123 + URL X.

Example: a favourite with DAN 123 + URL X, added directly with only URL X → same product by rule 2.

### 4.3 Matching (`resolve_items`)

For each term, compare `normalize(term)` against the favourites, stage by stage. The first stage with at least one hit decides:

1. **Alias** – exact match with a normalised alias → `resolved` (aliases are unique, so at most one hit).
2. **Name** – exact match with the normalised name → one hit `resolved`, several `ambiguous`.
3. **Category** – exact match with the normalised category → one hit `resolved`, several `ambiguous`.
4. No hit → `unknown`.

No substring or fuzzy matching. The server never picks one of several candidates.

### 4.4 Merging

- Items are applied in input order. Each item is compared (§4.2) with the **open** entries, including entries created or updated by earlier items of the same request, so duplicates within one request add up.
- Same product as exactly one open entry → that entry's quantity is increased. Missing identifiers (DAN, URL) in the entry's snapshot are filled from the item. Existing values are never overwritten.
- No matching open entry → a new open entry is created.
- Entries with status `bought` are never merged into. They stay stored and are excluded from the open list.
- A resulting quantity above 99 fails the whole request with `QUANTITY_LIMIT`.

### 4.5 Idempotency

- Every `add_to_shopping_list` call carries a client-generated `requestId`.
- The `requestId` lookup, the list changes and the new `ProcessedRequest` record all happen inside one `update(fn)` (§4.6), i.e. under the lock and in the **same atomic write**. Either everything is persisted or nothing is.
- Processed requests are persisted in the store file, so they survive restarts.
- Same `requestId` and same payload → the stored result is returned with `replayed: true`; the list is not changed.
- Same `requestId` and different payload → `REQUEST_ID_CONFLICT`; the list is not changed.
- Failed requests are not recorded; the client may retry them with the same `requestId`.
- Payload equality: SHA-256 over the canonical JSON (sorted keys) of the validated and normalised `items` array.
  - Normalisation follows §4.1–4.2 where applicable: text fields are trimmed and dm URLs are normalised, so equivalent spellings of a URL (e.g. with or without a trailing slash) count as identical.
  - Normalisation is independent of mutable favourite data: a `favoriteId` is hashed as given and is not resolved to the favourite's current fields. A later change to a favourite therefore cannot affect the replay of an already stored request.
  - Array order remains significant.

### 4.6 Storage

- **Path:** exactly one absolute store path, computed by one shared function used by both the MCP server and the UI:
  - The **project root** is the directory that contains this project's `package.json`. It is determined from the code's location, not from the working directory.
  - Default path: `<project root>/data/store.json` (git-ignored).
  - The env variable `EINKAUFSHELFER_DATA_FILE` overrides the default. A relative value is also resolved against the project root.
  - The MCP server logs the absolute path on start-up to stderr (stdout carries the protocol).
- **Interface:** storage is accessed through an interface (`read()`, `update(fn)`), so another adapter can be added later without changing the core.
- **Writing:** `update(fn)` runs read → modify → write under an exclusive **cross-process** file lock, because the MCP server and the UI are separate processes. The new content goes to a temp file in the same directory and is then renamed over the store file. Lock acquisition is retried for at most 5 s, then fails.
- **Rename on Windows:** another application may briefly hold the file open.
  - Rename is retried on `EPERM`/`EBUSY` with a short delay (50 ms), within a bounded timeout (2 s total), while retaining the exclusive lock.
  - The existing store file is never deleted before the rename. It is replaced only by the rename itself, so a failed replacement always leaves the previous store intact.
  - If retries are exhausted → `STORAGE_UNAVAILABLE`. The existing store stays unchanged and removal of the temp file is attempted.
  - If removing the temp file fails as well, the failure is logged (stderr) and the original storage error is returned. The cleanup failure never masks or replaces it, and the store file is not touched.
- **Missing file:** treated as an empty store (`version: 1`, empty arrays) and created on the first write.
- **Corrupt file:** invalid JSON, a schema violation or an unknown `version` → `STORAGE_CORRUPT`. The file is never overwritten in this case.
- **Inaccessible file:** cannot be read or written (e.g. missing permissions) → `STORAGE_UNAVAILABLE`.
- **Sample data:** fictional German sample favourites live in `data/sample-favorites.json` (committed). `npm run seed` writes them into an empty or missing store and refuses to overwrite a non-empty one.

### 4.7 Errors

Tool errors are returned as MCP tool results with `isError: true` and a JSON body `{ "code": string, "message": string, "details"?: object }`. Nothing is written when an error is returned.

| Code | When |
|---|---|
| `VALIDATION_ERROR` | Input violates the Zod schema, incl. whitespace-only text |
| `FAVORITE_NOT_FOUND` | A `favoriteId` does not exist |
| `PRODUCT_IDENTITY_CONFLICT` | Contradicting identifiers (§4.2) |
| `QUANTITY_LIMIT` | A resulting quantity would exceed 99 |
| `REQUEST_ID_CONFLICT` | Known `requestId` with a different payload |
| `DUPLICATE_ALIAS` | Phase 2: alias already in use |
| `STORAGE_UNAVAILABLE` | Lock timeout, missing permissions or other I/O failure |
| `STORAGE_CORRUPT` | Store file content is invalid (JSON, schema, version) |

## 5. Requirements

- **R1** The server exposes its tools over MCP stdio using the official TypeScript SDK.
- **R2** All tool inputs are validated with Zod before any logic runs.
- **R3** Core logic (`src/core/`) consists of pure functions without I/O and is unit-tested with Vitest.
- **R4** Matching, product identity, merging and idempotency follow §4 exactly.
- **R5** No tool reports success unless the change has been persisted.
- **R6** The storage guarantees in §4.5–4.6 are verified by integration tests. These use temporary files and, where concurrency matters, separate OS processes (§6.4). Unit tests of pure functions are not sufficient for them.
- **R7** Automated tests use structured inputs and fixed sample data only; they never call dm or an LLM.
- **R8** TypeScript runs in `strict` mode, plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. Code is formatted with Prettier.
- **R9** Code, comments and docs are in English; UI texts and sample data are in German.
- **R10** The README reflects the state actually reached. Planned features and checks that have not been run are clearly marked as such.

## 6. Tools and acceptance criteria

### 6.1 `resolve_items` (phase 1) – read-only

Input: `{ items: { term: string (1–200), quantity?: int 1–99 (default 1) }[] }` (1–50 items)
Output: `{ results: Result[] }` in input order, where `Result` is one of
`{ term, quantity, status: "resolved", favorite }` · `{ term, quantity, status: "ambiguous", candidates: Favorite[] }` · `{ term, quantity, status: "unknown" }`

- **AC-R1** A term equal to an alias, ignoring case and extra whitespace (`"  Die üblichen  FEUCHTTÜCHER "`), is `resolved` to that favourite and returns the given quantity.
- **AC-R2** A term matching one favourite's alias and another favourite's name resolves to the alias owner.
- **AC-R3** A term matching the names of two favourites is `ambiguous` and lists both.
- **AC-R4** A term matching the category of two favourites (and no alias/name) is `ambiguous` with both; with one favourite in that category it is `resolved`.
- **AC-R5** A term without any hit is `unknown`; a substring of an alias (`"feucht"`) is also `unknown`.
- **AC-R6** The store is unchanged after the call.
- **AC-R7** Empty `items`, an empty or whitespace-only term, or quantity `0` / `100` / `1.5` → `VALIDATION_ERROR`.

### 6.2 `add_to_shopping_list` (phase 1)

Input:
```ts
{
  requestId: string;            // 1–128 chars, [A-Za-z0-9_-]
  items: (                      // 1–50 items
    | { favoriteId: string; quantity: number }
    | { product: ProductRef; quantity: number } // needs dmArticleNumber or dmUrl
  )[];
}
```
Output (`AddResult`): `{ requestId, replayed: boolean, entries: { entryId, name, quantity, action: "created" | "merged" }[] }`, one per input item in input order, where `quantity` is the entry's new total.

- **AC-A1** Adding a favourite that is not on the open list creates one open entry with the given quantity.
- **AC-A2** A new request (new `requestId`) for a product already on the open list increases that entry's quantity; no second entry is created.
- **AC-A3** A product added directly with DAN X merges with an open entry created via a favourite with DAN X, and vice versa.
- **AC-A4** Mixed identifiers: a favourite with DAN 123 + URL X is on the open list. Adding the same product directly with only URL X merges into that entry. The reverse order also merges, and the entry then carries both DAN 123 and URL X.
- **AC-A5** Without a DAN, two dm URLs that differ only in query string, fragment, trailing slash or host case merge.
- **AC-A6** Two favourites without dm identifiers but with the same name produce two separate entries.
- **AC-A7** If the only existing entry for a product has status `bought`, adding the product creates a new open entry; the bought entry is unchanged.
- **AC-A8** Retrying with the same `requestId` and the same items returns the original result with `replayed: true`; quantities are unchanged. This also holds when the retry spells a dm URL differently (e.g. trailing slash, query string, host case) or adds surrounding whitespace to a text field.
- **AC-A9** Same `requestId` with different items (including the same items in a different order) → `REQUEST_ID_CONFLICT`; store unchanged.
- **AC-A9a** A favourite is changed after a successful request (simulated by editing the store). Retrying the request with the same `requestId` and items still returns `replayed: true`, not `REQUEST_ID_CONFLICT`.
- **AC-A10** One unknown `favoriteId` among valid items → `FAVORITE_NOT_FOUND`; nothing is written and the `requestId` is not recorded.
- **AC-A11** A resulting quantity of 100 → `QUANTITY_LIMIT`; store unchanged.
- **AC-A12** A direct product without DAN and URL, with a non-dm URL, with the dm start page as URL (also together with a DAN), or with a whitespace-only name → `VALIDATION_ERROR`.
- **AC-A13** An item with DAN 456 + URL X, while an open entry has DAN 123 + URL X → `PRODUCT_IDENTITY_CONFLICT`; store unchanged. The same applies when an item matches two open entries.
- **AC-A14** If the write fails (simulated), the tool returns `STORAGE_UNAVAILABLE`, the file content is unchanged and no success is reported.
- **AC-A15** If the store file is corrupt, the tool returns `STORAGE_CORRUPT` and the file is left byte-for-byte unchanged.

### 6.3 `get_shopping_list` (phase 1) – read-only

Input: none. Output: `{ entries: ListEntry[] }` – open entries only, ordered by `addedAt` ascending.

- **AC-L1** Returns all open entries with their current quantities.
- **AC-L2** Entries with status `bought` are not returned but remain in the store.
- **AC-L3** A missing store file returns an empty list and does not create the file.
- **AC-L4** A store file with invalid content → `STORAGE_CORRUPT`; an unreadable file (e.g. no permission) → `STORAGE_UNAVAILABLE`.

### 6.4 Storage integration tests (phase 1)

These run against temporary store files.

- **AC-ST1** Two separate OS processes concurrently add different products to the same store file. Afterwards both changes are present.
- **AC-ST2** A request succeeds and the store is then reopened by a new process. Repeating the same `requestId` returns `replayed: true`, and the quantity is not increased again.
- **AC-ST3** Two processes send the same request (same `requestId`, same items) concurrently. The quantity is increased exactly once; one response has `replayed: false`, the other `replayed: true`.
- **AC-ST4** The path function returns the same absolute path when called from different working directories. A relative `EINKAUFSHELFER_DATA_FILE` is resolved against the project root.
- **AC-ST5** The rename fails with `EPERM`/`EBUSY` a few times and then succeeds (simulated). The write succeeds.
- **AC-ST6** The rename keeps failing until the timeout (simulated). The result is `STORAGE_UNAVAILABLE`, the store file is byte-for-byte unchanged and no temp file is left behind.
- **AC-ST7** The rename keeps failing and removing the temp file also fails (simulated). The result is still `STORAGE_UNAVAILABLE` for the original rename failure, the cleanup failure is logged and the store file is byte-for-byte unchanged.

### 6.5 `get_favorites` (phase 2) – read-only

- **AC-F1** Returns all favourites with name, category, aliases and dm identifiers.

### 6.6 `save_favorite` (phase 2)

Input: `ProductRef` with required `category` and optional `aliases`.

- **AC-S1** A valid favourite is stored with a new `id` and returned.
- **AC-S2** An alias that collides (after normalisation) with an existing alias or another alias in the same input → `DUPLICATE_ALIAS`; nothing is stored.
- **AC-S3** Duplicate names are allowed.
- **AC-S4** A whitespace-only name, category or alias → `VALIDATION_ERROR`.

### 6.7 UI (phase 3) – outline

- **AC-U1** The shopping list page shows open entries with name and quantity, reading the store on every request.
- **AC-U2** "Gekauft" sets status `bought` and `boughtAt`; the entry disappears from the open list.
- **AC-U3** "Entfernen" deletes the entry.
- **AC-U4** Favourites are listed read-only.
- UI writes use the same storage `update(fn)` and the same path function as the MCP server.

## 7. Assumptions

- **A1** Available dm identifiers (DAN, URL) are taken over. A direct product without any suitable identifier is rejected, because it could never be merged safely. Which identifiers dm's MCP server actually returns is still to be checked in phase 2.
- **A2** All query parameters of dm product URLs are treated as tracking parameters. The product is identified by the URL path.
- **A3** The DAN is a digit string. Its exact length is not validated beyond 1–13 digits.
- **A4** A list entry keeps the product snapshot (name, category) from when it was created. Merges only change the quantity and fill missing identifiers.
- **A5** Processed `requestId`s are kept indefinitely in v1. The expected volume is small for a single family.
- **A6** If two favourites share a dm identifier, they count as the same product and merge on the list. `save_favorite` does not reject this.
- **A7** "Remove" in the UI deletes the entry permanently. "Bought" keeps it.
- **A8** Next.js may bundle the code, so the location-based project-root lookup could be unreliable there. In that case the UI determines the project root from its own start-up directory, which Next.js requires to be the project root. AC-ST4 covers the MCP side.
- **A9** Cross-process lock: `proper-lockfile`, lock directory `<store file>.lock` next to the store. The holder refreshes the lock's mtime, nominally every 1 s; a lock whose mtime is older than 4 s (stale time) counts as abandoned and is taken over by the next process that tries to lock. An actively refreshed lock is never taken over, however long others wait; they fail after 5 s with `STORAGE_UNAVAILABLE`. After a crash, writes work again once the left-behind lock is older than 4 s. Limits: detection relies on the lock's mtime and on the holder's event loop. A holder that is suspended or blocked for longer than the stale time can lose its lock. The loss is only noticed at the holder's next refresh attempt that actually runs. Nominally that is about 1 s later, but a paused process or a blocked event loop can delay it further, so detection within a fixed time is not guaranteed. The holder checks the known lock state before writing and immediately before every rename attempt, including retries; once the loss is known it starts no further rename, removes its own temp file (best effort), returns `STORAGE_UNAVAILABLE` and leaves the store file and the now foreign lock untouched. A rename that has already started, or that starts before the loss is noticed, cannot be undone, so this is no complete protection against arbitrary process pauses. Only processes on the same machine and local file system are supported (no network shares), and programs that edit the file without taking the lock are not prevented from doing so.
- **A10** Temp files are named `.<store file name>.<pid>.<uuid>.tmp`, live in the store directory and are flushed to disk before the rename. A temp file left behind by a crash is not removed automatically. A new state is validated against the store schema before it is written; invalid content is refused with `STORAGE_CORRUPT` and nothing is written. An empty `EINKAUFSHELFER_DATA_FILE` counts as unset.
- **A11** The store file is checked strictly: unknown fields, untrimmed text, non-normalised dm URLs, IDs that are not UUIDs, timestamps that are not UTC, `boughtAt` without status `bought` (or the reverse), and duplicate favourite IDs, entry IDs, aliases (after normalisation) or `requestId`s make it `STORAGE_CORRUPT`. List entries may refer to favourites that no longer exist.
- **A12** `npm run seed` treats a store as empty only if it has no favourites, no list entries and no processed requests; otherwise it changes nothing and exits with code 1. Invalid sample data is rejected with `VALIDATION_ERROR`.

## 8. Out of scope (v1)

- Calling dm's MCP server from this server; combining the two servers is the AI client's job.
- Natural-language parsing, fuzzy, substring, plural or umlaut-folding matching.
- Editing or deleting favourites.
- MCP tools for marking items as bought or removing them (UI only).
- Units, prices, stock, stores.
- Live updates in the UI (push, polling).
- Multiple lists, users, authentication, remote hosting.
- Pruning of processed `requestId`s; schema migrations beyond `version: 1`.
- Purchase-interval suggestions, external list sync, voice input (see README roadmap).
- Automated tests against dm's live server or an LLM; the end-to-end flow with Claude and dm is checked manually and documented.
